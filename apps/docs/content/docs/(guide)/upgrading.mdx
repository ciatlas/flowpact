---
title: Upgrading
description: What changes between flowpact releases, and what to do when you move to a new one.
---

A minor release can change what is reported. An incompatible change to the CLI, the configuration, the action, the
reports or the API is a major release (the next one is 1.0.0); up to 0.14, a minor release could make one too.

## Move to a new version

- **GitHub Action:** `uses: ciatlas/flowpact@v0.<minor>` with the new minor version. Before 1.0 the floating tag
  follows a minor release, so `@v0.22` stays on 0.22.
- **CLI:** `npx flowpact@0.<minor>`, or update the dev dependency.
- **VS Code:** the extension updates itself.

Then read the sections below from your version up.

## 0.21 → 0.23

Nothing to change. What is new:

- **Editor:** [quick fixes](/docs/editors#quick-fixes), **Accept this finding with an override**,
  [rename](/docs/editors#rename), and hover and go to definition in contract files. A repository with no `.github`
  folder, such as an action's, is now analyzed, so its findings appear.
- **Reports:** a finding flowpact can fix with certainty carries `suggestions` in the
  [JSON report](/docs/cli#json-report) and `fixes` in SARIF. Both are additions to the existing schemas.

## 0.20 → 0.21

### Remote interfaces lockfile

`flowpact remotes update` now records, for a remote reusable workflow, the secrets it reads without declaring them
(`undeclaredSecrets`), and [FP205](/docs/rules/fp205) reports a call of it without `secrets: inherit`. The first
`remotes update` lists those entries as `changed`, though their commits are the same.

flowpact 0.20 and earlier refuse a lockfile with this key (FP611) and then check no remote call. **Update every
flowpact that reads the lockfile (the action's pin, the CLI, the editor extension) before running `remotes update`
with 0.21.** From 0.21, a key a later version adds is ignored instead.

### New findings

FP205 reports calls of remote reusable workflows without `secrets: inherit` whose secrets the lockfile records, and,
with `--fetch-remotes` or the action's `remotes: fetch`, those it fetches for the run. Use `secrets: inherit`, or add
an override on the symbol (`octo/ship/.github/workflows/ship.yml@v1#secrets.NPM_TOKEN`). FP205 no longer reports a
read where GitHub allows no `secrets` (an input default, a `workflow_call` output, `jobs.<id>.with`, `if` or `name`).

[FP612](/docs/rules/fp612) also reports a lockfile entry that records another commit than the full commit SHA its
reference pins (`octo/setup@<sha>`). `remotes update` never writes one, so only an edited lockfile has it; flowpact no
longer checks calls against such an entry. Run `flowpact remotes update` to correct it.

### Sources cache

`flowpact remotes update` now keeps the workflow files and `action.yml`s it reads in a per-user
[sources cache](/docs/remote-interfaces#sources-for-the-editor), for go to definition in the editor, and prunes it to
the 3 most recently used commits of each repository. Nothing to do: it keeps nothing in CI unless you ask
(`--cache-dir`), and `--no-cache` turns it off. `remotes update` also no longer loads the plugins your config lists: it
runs no rule.

<Accordion title="0.19 → 0.20" id="from-0-19-to-0-20">

**Remote interfaces lockfile**

0.20 writes a leaner lockfile: an input or secret is marked `required: true` only when it is, and `required: false`
is left out. An entry read on github.com through the new opt-in fallback records `host: github.com`. flowpact 0.19
refuses such a lockfile ([FP611](/docs/rules/fp611)) and then checks no remote call, so **update every flowpact that
reads the lockfile (the action's pin, the CLI, the editor extension) before running `remotes update` with 0.20**.

`flowpact remotes update` takes paths, like the other commands, to fetch only what given workflows and actions use;
a path that names nothing is an error (exit 2). It shows its progress and the source of its token, and says why a
reference could not be fetched.

**GitHub Enterprise Server and GHE.com**

`--github-com` (the action's `remotes-github-com` and `github-com-token` inputs) also looks on github.com for the
references the enterprise server lacks, as the runner does through GitHub Connect. It is opt-in, because it sends
those references' names to github.com; see
[Remote interfaces](/docs/remote-interfaces#github-enterprise-server-and-ghecom).

</Accordion>
<Accordion title="0.18 → 0.19" id="from-0-18-to-0-19">

0.19 checks calls into other repositories, once you record their interfaces, and grades more kinds of change in
impact mode.

**Remote interfaces**

`flowpact remotes update` writes `.github/flowpact/remotes.lock.yaml`, the interfaces of the reusable workflows and
actions you call from other repositories. With it committed, those calls are checked like local ones
(FP101–FP103, FP201, FP202, FP301), and [FP603](/docs/rules/fp603) no longer reports a remote workflow the lockfile
has. Without a lockfile nothing changes. Two new rules apply only when there is one:
[FP611](/docs/rules/fp611) (error) for a lockfile that cannot be used, and [FP612](/docs/rules/fp612) (warning) for
one that lacks a reference the repository uses or has one it no longer uses, as after a Renovate or Dependabot
update. The action reads the lockfile as committed; `remotes: fetch` fetches what it lacks for the run. See
[Remote interfaces](/docs/remote-interfaces).

0.19.1 records references it cannot read under the lockfile's `unreadable:`, which 0.19.0 refuses (FP611). Use
0.19.1 or later wherever the lockfile is read.

**Impact mode grades more**

Impact mode now also grades what a published reusable workflow or action does in its callers' runs, so a pull request
can require more than before:

| Change | Required |
| --- | --- |
| An output is now set only when an `if:` holds | major, uncertain ([FP814](/docs/rules/fp814)) |
| A job needs a runner label or group callers may not have | major (uncertain when chosen at run time) |
| A job gains, changes or loses its `environment:` | minor |
| An artifact callers download is no longer uploaded, or renamed | major |
| Jobs or steps changed, and nothing else is graded | patch |

A patch never fails a pull request, so most repositories see the change only in the verdict: a `chore:` pull request
that changes steps now reports "requires patch" ([FP813](/docs/rules/fp813)) instead of "none". A pull request whose
title declares less than a minor or major it now requires fails with [FP810](/docs/rules/fp810); declare the release
it needs, or accept the finding with an [override](/docs/configuration#overrides). See
[Impact mode](/docs/impact-mode).

</Accordion>
<Accordion title="0.17 → 0.18" id="from-0-17-to-0-18">

0.18 writes new contracts as `.contract.yaml` and reads `.contract.yaml` and `.contract.yml` alike. Existing contracts
keep their names, so a repository that locks contracts sees no change.

**Contract file names**

`flowpact generate` names a new contract `.contract.yaml`, except in a repository whose contracts are all
`.contract.yml`, where it keeps to `.contract.yml` so the directory has one extension. A contract named either way is
read, compared and updated under its own name. To move a repository to `.contract.yaml`, rename its contract files
(`git mv`): each contract names its unit, so a renamed file is still that unit's contract, and `flowpact check` stays
clean. Where tooling or `CODEOWNERS` matches `*.contract.yml`, match `*.contract.yaml` too.

</Accordion>
<Accordion title="0.16 → 0.17" id="from-0-16-to-0-17">

0.17 follows secrets as GitHub holds them, and places some findings more exactly. No finding is added or removed: what
changes is where a few findings are, and what `flowpact trace`, the editor, the JSON report's graph and custom rules see
of secrets.

**Finding locations**

A finding on an expression that spans lines in a block scalar, or on a double-quoted scalar with escapes, now ends where
the expression ends in the file: [FP502](/docs/rules/fp502)'s range, for example, ended early. A reference written after
a property that follows a dot and spaces or a line break (`fromJSON(x). inputs.a`) is now located at the reference, not
at the property, and so is an expression whose `${{` or `}}` is written with an escape (`\x7d`). A finding's
fingerprint does not include its location, so code scanning keeps these alerts.

**`flowpact trace`, the editor and custom rules**

`flowpact trace` now names the workflow of a secret or input that no file declares, such as a secret a called workflow
reads through `secrets: inherit` without declaring it: `<workflow>#secrets.<name> (unresolved)`, where 0.16 showed
`secrets.<name> (unresolved)` alone. In `--format json`, such a node has the workflow as its `unit` and
`secrets.<name>` as its `label`.

A whole or computed `secrets` (`toJSON(secrets)`, `secrets[inputs.name]`) now also reads each secret the workflow reads
by name or is passed by name, and its `GITHUB_TOKEN`; in a workflow that callers hand every secret to through
`secrets: inherit`, also each secret those callers declare, read by name or are passed by name. `flowpact trace` and the
editor's hover list them, and the editor's references of such a secret include the whole read. `secrets: inherit`
follows a secret to the other workflow's own spelling of it, in any letter case, both ways, and no longer to a caller's
`GITHUB_TOKEN`, which GitHub gives every workflow itself. The JSON report's graph, and the symbol and edge counts in the
summary, gain these secrets.

**Custom rules:** `usagesOf` lists a whole or computed `secrets` read as a usage, marked `whole`, of each of the secrets
above. A secret read by name, and `GITHUB_TOKEN`, now have these usages next to their reads by name, and an inherited
secret that the workflow does not name, which had no usage, now has them.

</Accordion>
<Accordion title="0.15 → 0.16" id="from-0-15-to-0-16">

0.16 follows inputs that a workflow reads through `github` as GitHub does. A workflow's own inputs are in
`github.event.inputs` only when the workflow is dispatched. When it is called, GitHub gives it the caller's `github`
context, so there `github` never holds what the caller passes in `with:`. Some findings change, and each change below
says what to do about it.

**New and changed findings**

- [FP104](/docs/rules/fp104) reports more inputs that nothing reads:
  - in a workflow that can be both dispatched and called, an input that only `workflow_call` declares and that is
    read only as `github.event.inputs.<name>`;
  - in a workflow or composite action that reads `toJSON(github.event)`, `toJSON(github.event.inputs)` or
    `github.event.inputs[<expression>]`, any input other than a `workflow_dispatch` input that nothing else reads (0.15
    skipped every input of such a workflow or action);
  - a dispatch input read only through `github` in the workflow's own input defaults or `workflow_call` outputs, which
    GitHub evaluates only when the workflow is called.

  Remove the input, or read it as `inputs.<name>`, which holds a workflow's `workflow_dispatch` inputs when it is
  dispatched and its `workflow_call` inputs when it is called (and an action's own inputs). An input default or
  `workflow_call` output is evaluated only when the workflow is called, so to read a dispatch input there, also declare
  it under `workflow_call`.
- [FP105](/docs/rules/fp105) now reports a condition that reads an optional dispatch input without a default as
  `github.Event.Inputs.<name>`, in any letter case, as it did for `github.event.inputs.<name>`: give the input a
  default, or compare it explicitly, as for `inputs.<name>`. It no longer reports a condition that reads, as
  `github.event.inputs.<name>`, an input that only `workflow_call` declares, since the condition never reads that input:
  FP104 reports the input if nothing else reads it.
- [FP106](/docs/rules/fp106) now also reports a passed input that the called workflow reads only through a step's own
  `env:` value that reads `github`, where the step reads that value as `env.<name>`, or only through
  `toJSON(github.event)`, `toJSON(github.event.inputs)` or `github.event.inputs[x]`, and a passed input that such a
  workflow never reads (0.15 skipped those workflows). For an input read only through `github`, the message now says it
  is read "only through the github context, the caller's when it is called". 0.15 said "only through
  github.event.inputs, the caller's event when it is called" for `github.event.inputs.<name>`, and "never reads it" for
  `toJSON(github)`, `github.event[x]` and `github.Event.Inputs.<name>` in another letter case. In a called workflow that
  can also be dispatched, an input that only `workflow_call` declares and that is read as
  `github.event.inputs.<name>`, or one read through `github` only in the workflow's own input defaults or
  `workflow_call` outputs, is now reported as never read. Read the input as `inputs.<name>` in the called workflow, or
  stop passing it.
- [FP401](/docs/rules/fp401) no longer reports an optional input with an empty default (none, or `default: ''`)
  passed to a workflow that can be called when the conditions that read it read it only through `github`, which never
  holds what the caller passes. A required input, or one whose non-empty default the empty value replaces, is still
  reported.

Delete the overrides that [FP902](/docs/rules/fp902) now reports: FP105 and FP401 findings that are gone leave their
overrides matching nothing. The reworded FP106 findings keep their overrides, which match the rule, target and file,
not the message. Code scanning closes the alerts of reworded findings and opens new ones once, because an alert's
fingerprint includes its message.

**`flowpact trace`, the editor and custom rules**

`flowpact trace` and the editor follow reads of `github` the way the findings do. `flowpact trace` now follows
`toJSON(github)` and `github.event[x]`, and the editor lists them among a dispatch input's references. Trace, hover,
go-to-definition and references now follow `github` reads and step outputs written in another letter case
(`github.Event.Inputs.<name>`, `steps.<id>.Outputs.<name>`), and the editor resolves `needs.<job>.Outputs.<name>` to
the output rather than the job. They no longer follow `github` in a workflow's own input defaults and `workflow_call`
outputs, nor `github.event.inputs.<name>` for an input that no `workflow_dispatch` declares. The JSON report's graph,
and the symbol and edge counts in the summary, change with them.

**Custom rules:** in a workflow that can be dispatched, `usagesOf` for a `workflow_dispatch` input now also lists:
- whole or computed `github` reads (`toJSON(github)`, `github.event[x]`), marked `whole`, also through a step's own
  `env:` value;
- `github.Event.Inputs.<name>`, in any letter case.

`usagesOf` no longer lists:
- `github.event.inputs.<name>` as a usage of an input that only `workflow_call` declares, or of a name that no trigger
  declares;
- for a `workflow_dispatch` input, reads of `github` in the workflow's own input defaults and `workflow_call` outputs.

A read of one output written in another letter case (`needs.<job>.Outputs.<name>`, `steps.<id>.Outputs.<name>`) is no
longer marked `whole`, and a `run:` step's output read that way is now a usage. A rule about the value a caller passes
should skip usages through `github` (see `Usage.whole` in the API types).

</Accordion>
<Accordion title="0.14 → 0.15" id="from-0-14-to-0-15">

0.15 changes what some runs report. Each change below says what to do about it.

**Impact mode honours paths**

[Impact mode](/docs/impact-mode#only-some-units) with paths (`lint --impact <paths>`, `check --impact <paths>`, the
action's `paths` input with `impact`, the API's `paths`) now grades only the published workflows and actions within
them. Before, it graded every published unit but reported only the findings about files within the paths, so a
breaking change elsewhere could pass silently: the verdict said `required major` and the run passed. Now the verdict
and the findings agree. If your impact check passes paths, it now guards only the units within them: drop the paths
to gate every published unit. `flowpact impact` takes paths too, where 0.14 refused them.

A removed or renamed unit is graded only when its old path, or a directory holding it, is among the paths, so prefer
directory paths (`actions/`) in the action's `paths` input; a path that names only the removed unit fails later pull
requests once the removal is merged. A path the change removed is no longer refused as missing in impact mode. Where
impact mode is skipped on `merge_group` or `push`, such a path is only warned about, as is a removed action's directory
that keeps other files, and so is a mistyped path: without a baseline the two cannot be told apart. These events
usually follow a pull request's run, which has the baseline and refuses a mistyped path, but not always: the first
push of a new branch comes before any pull request, and a workflow that runs only on `push` with `impact: auto` never
refuses one, where 0.14 failed. To have such a workflow refuse it, use `impact: on`, which compares each push with the
commit before it (a new branch's first push, which has none, still only warns). On other events, a skipped impact mode
still refuses these paths.

`flowpact graph` takes paths as well, and then draws only those workflows and actions and what they call.

**Orphaned contracts within the paths**

`flowpact check <paths>` reports the orphaned contract (`FP804`) of a workflow or action that no longer exists when
its path lies within the paths, and `flowpact generate <paths>` deletes it; 0.14 left it to runs without paths. A
`check` job with paths may now fail on such a contract: run `flowpact generate` to delete it.

**Impact mode leaves ignored units out**

A published workflow or action whose file both the baseline's `ignore` and the pull request's match is no longer
graded. 0.14 graded it but dropped its findings, so the verdict could say `required major` while the run passed. Now
the verdict and the findings agree, and impact mode's findings are never dropped by `ignore`. If an ignored unit is one
you publish, remove it from `ignore` to gate its changes: the pull request that removes it is already graded for it.
When `ignore` leaves out every published unit, `impact: auto` skips the run as in a repository that publishes nothing,
and `impact: on` reports the verdict on the first workflow or action file (within the paths) that is not ignored, or
is skipped, saying so, when every one is. The reports name the published units `ignore` left out (`left out by
ignore: …`, and `impact.ignored` in the JSON report).

Because a unit is left out only when the baseline's `ignore` matches it too, a pull request's own `ignore` edit cannot
take a published unit out of its check: a pull request that adds one to `ignore` is still graded for it. Where it
under-declares, it now fails with `FP810`, where 0.14 dropped the finding and passed with `impact-ok: false`. Every
other finding follows the pull request's own `ignore`, as before.

A [base config](/docs/impact-mode#configuration) that the checked-out commit does not track, such as the
organization's config checked out into an ignored directory of the workspace, now counts on both sides, as one outside
the repository does: the published units its `ignore` matches are left out, and its impact settings apply to the
baseline too, where 0.14 left them out as those of a file of the repository. A base config within a submodule is the
pull request's own, as a file of the repository is, and its `ignore` counts on the baseline's side as the baseline's
commit of the submodule has it.

</Accordion>
<Accordion title="0.13 → 0.14" id="from-0-13-to-0-14">

0.14 reads more of what workflows write: a read of a whole object or through a computed key (`toJSON(inputs)`,
`matrix[inputs.key]`, `secrets.*`), an input's `default:` where a caller omits the input, and `github.event.inputs`
in a workflow that can be called, which holds the caller's event there. A few findings change with it.

**Regenerate your contracts**

A call to a reusable workflow whose matrix has an `include` or `exclude` item that is an expression
(`- ${{ fromJSON(inputs.extra) }}`) now records its matrix as `exact: false`, since that item is only known at runtime;
with such an `exclude` item it also records the combinations it knows, where 0.13 recorded none. If you lock
contracts, `flowpact check` reports [FP802](/docs/rules/fp802) for such a call until you run `flowpact generate` and
commit the result.

**New and changed findings**

- **[FP404](/docs/rules/fp404)** no longer reports a matrix key as missing from every combination when an `exclude`
  item is an expression: such an item removed every combination before.
- **[FP403](/docs/rules/fp403)** (info) now notes a matrix whose `include` has an item that is an expression: the keys
  it adds are only known at runtime.
- **[FP104](/docs/rules/fp104) and [FP203](/docs/rules/fp203)** no longer report an input or a secret that is read
  through a `*` filter (`inputs.*`, `github.event.inputs.*`, `secrets.*`), nor [FP106](/docs/rules/fp106) a value
  passed to an input that the callee reads through `inputs.*`.
- **[FP106](/docs/rules/fp106)** now reports a value that a caller passes to a workflow which reads the input only
  through `github.event.inputs`: when the workflow is called, that is the caller's event, not the value passed.
- **Locations:** a finding placed at the start of a bare `if:` written as a block scalar (`if: |`) or a quoted scalar,
  such as [FP505](/docs/rules/fp505) for `hashFiles()` in a job's `if:`, now points at the expression rather than at
  the `|` or the quote, and a reference whose text also appears earlier inside a string literal is located at the
  reference. Code scanning may close and reopen those alerts once.

**`flowpact trace` and custom rules**

- `flowpact trace --up` also ends at an omitted input's `default:`, follows a whole read to each member, and shows a
  `github.event.inputs` read in a workflow that can be called as the dispatch input `(when dispatched)` next to the
  caller's event. The tree now prints each branch's note, such as `(exposed to the caller)`. See
  [`flowpact trace`](/docs/cli#flowpact-trace).
- In [custom rules](/docs/custom-rules), `usagesOf` now includes whole and computed reads of `inputs`, `matrix`,
  `secrets` and `env`, marked `whole`. A rule about how one specific input or key is read should skip them.

</Accordion>
<Accordion title="0.11 → 0.12" id="from-0-11-to-0-12">

The action moved to `ciatlas/flowpact`. GitHub redirects the old name, so `rumankazi/flowpact@v0.11` and older
references keep working, but use the new one from now on.

flowpact moved to the [ciatlas](https://github.com/ciatlas) organization: the repository is now `ciatlas/flowpact` and
the docs are at [ciatlas.github.io/flowpact](https://ciatlas.github.io/flowpact). The npm package, the VS Code extension and the GitHub Marketplace
listing keep their names, and nothing changes in what flowpact reports.

**Regenerate your contracts**

Contracts name their schema and docs by URL, and both moved. Until you run `flowpact generate` once and commit the
result, `flowpact check` reports [FP802](/docs/rules/fp802) for every contract written by 0.11 or earlier. If your
`.github/flowpact/flowpact.config.yml` starts with a `# yaml-language-server: $schema=` line (for editor completion),
point it at `https://ciatlas.github.io/flowpact/schemas/config/v1.json`: the old docs and schema URLs under
`rumankazi.github.io/flowpact` no longer resolve.

**Verifying older releases**

Releases up to 0.11.1 were built before the move, and GitHub keeps their attestations under the old owner: verify
them online with `--owner rumankazi`, or offline against the bundle attached to the release with
`gh attestation verify <file> --bundle <file>.sigstore.json --repo rumankazi/flowpact`. `gh release verify` no longer
finds their release attestations. See [verify a release](/docs/security#verify-a-release).

</Accordion>
<Accordion title="0.9 → 0.10" id="from-0-9-to-0-10">

0.10 is for organizations that build on flowpact: a [programmatic API](/docs/api) with a function per command, the
action's `base-config` and `plugin` inputs for a [copy of the action](/docs/integrating#copy-the-action), and an action
about a third of its old size. Nothing changes for workflows that use the action or the CLI as before, except a copy of
the CLI's `dist/index.js` on its own ([below](#a-vendored-cli-is-its-whole-package-folder)).

**A vendored CLI is its whole package folder**

The npm package's `dist/index.js` now loads a second file next to it (code it shares with the API), so a copy of
`dist/index.js` alone no longer runs. It fails with exit code `1`, the code for findings:

```text
Error [ERR_MODULE_NOT_FOUND]: Cannot find module '…/dist/chunk-<hash>.js' imported from …/dist/index.js
```

Keep the package's whole `package/` folder, as [Run the CLI in a step](/docs/integrating#run-the-cli-in-a-step) shows:
`node tools/flowpact/dist/index.js lint …`. The second file's name changes with each release, so to update, replace
the folder rather than copy the new files into it.

</Accordion>
<Accordion title="0.8 → 0.9" id="from-0-8-to-0-9">

0.9 is for organizations that run flowpact in their own action or CI template ([Roll it out across an organization](/docs/integrating)):
GitHub annotations from the CLI, several reports from one run, `--plugin` and `--no-plugins`, and a
[base config](/docs/configuration#base-config). One change can fail a CI run: options must come after the command.

**Put options after the command**

Before 0.9, an option written before the command was dropped without a word: `flowpact --no-plugins lint` ran with the
repository's plugins, and `flowpact -q lint` was not quiet. 0.9 stops with a usage error (exit `2`) instead. Write
`flowpact lint --no-plugins`. `flowpact --help` and `flowpact --version` work as before.

**Config entries for rules that are not loaded**

A `rules:` or `overrides:` entry for a rule that no loaded plugin defines used to stop the run with a config error. 0.9
ignores it with a warning, so a repository can configure organization rules that only its organization's wrapper
loads. An unknown code with the built-in prefix (`FP999`), or a typo of a loaded rule (`unused-inptu`), is still an
error; see [Rules that are not loaded](/docs/configuration#rules-that-are-not-loaded).

</Accordion>
<Accordion title="0.7 → 0.8" id="from-0-7-to-0-8">

0.8 removes most false positives found on 28 large public repositories, so most repositories see fewer findings.
Two things can still fail a CI run right after the upgrade: contracts written by 0.7, and overrides for findings 0.8 no
longer reports.

**Regenerate your contracts**

If the repository locks its contracts (`.github/flowpact/contracts/`), run `flowpact generate` and commit the result.
0.8 records more of each interface:

- A read of a whole outputs object, such as `toJSON(needs.build.outputs)` or `needs.build.outputs[matrix.key]`, now
  counts as reading every output in it, and the callee's contract lists them.
- Actions used through a checkout `path:` or the new `$/` syntax now resolve, so their callers appear under `uses`.

Until then, `flowpact check` reports those contracts as [FP802](/docs/rules/fp802) (contract-outdated, an error).
In `mode: check` the action attaches the regenerated contracts as an artifact and a patch.

**Remove overrides that no longer match**

Overrides written for findings that 0.8 no longer reports match nothing. [FP902](/docs/rules/fp902)
(override-unused, a warning) names each one so you can delete it:

- **FP606** for actions used through a checkout `path:`: a step's `uses: ./path` now resolves against the runner's
  workspace, as GitHub does.
- **FP303** for outputs of published units: reusable workflows whose file name does not start with `_`, and the root
  `action.yml`, or exactly the units in [`impact.publish`](/docs/impact-mode#configuration) when it is set.
- **Findings inside [generated files](/docs/configuration#generated-files)** (`*.lock.yml`, or a header such as
  `DO NOT EDIT`), for the rules about a file's own internals: FP104, FP105, FP203, FP204, FP303, FP304, FP604, FP605
  and FP607.
- **FP105, FP205, FP401, FP402 and FP404** where the workflow already handles the empty value: a fallback
  (`matrix.k || 'x'`), a comparison, a quoted shell test, or a caller whose inputs skip the step.
- **FP302** for a job's own `if:` that reads a job it depends on indirectly: GitHub makes those visible there.
- **FP503** for background steps and `cache-mode`, which GitHub runs.

**New and changed findings**

- **[FP610](/docs/rules/fp610) (workspace-unverified, info)** marks a step's `uses: ./…` that flowpact cannot read,
  such as a path inside another repository's checkout. Write `owner/repo/path@ref` to have those actions checked, or
  set `FP610: off`.
- **[FP606](/docs/rules/fp606)** can fire where it was silent: an action of this repository used as `./…` in a job that
  checks the repository out only in a subdirectory, or a composite action's `./path` that works for one caller and not
  for another.
- **[FP105](/docs/rules/fp105)** now also reports published units when every local caller passes the input, because
  callers in other repositories can still omit it.
- **[FP401](/docs/rules/fp401)** is a warning when the empty value replaces a non-empty `default`, and is not reported
  when the input is optional with an empty default that no condition reads (or reads only through a fallback).
  **[FP404](/docs/rules/fp404)** reports a fallback that always applies as info.
- **[FP503](/docs/rules/fp503)** reports keys GitHub accepts and ignores, such as a top-level `env:` in `action.yml`,
  as warnings.
- If a hand-written file is treated as generated, list it under `generated.exclude`. If other repositories use an action
  in a subdirectory, list it under `impact.publish`; that setting replaces the default list, so include your other
  published units too.

**Code scanning alerts**

A finding's fingerprint includes its message. Messages changed for some FP105, FP205, FP302, FP401, FP404 and FP503
findings, so those alerts close and reopen once. If you had dismissed one, dismiss the new alert again.

**`flowpact generate` with paths**

`flowpact generate <paths>` now writes only the contracts of those workflows and actions, and leaves the others
(including orphaned ones) alone. A path that names no workflow or action exits with code 2.
