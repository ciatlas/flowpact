## Why it matters

Consumers pin a floating tag (`@v1`) or a version range and take every release in it, and read the version to judge an update. A change released at a lower level than it needs reaches them without warning: a breaking one released as a minor or patch leaves their required status check waiting forever or fails their run, and a new environment or check released as a patch changes their runs where they expected fixes only.

## How to fix

Declare the required impact (for example retitle the pull request `feat!: …` for a major release), or keep the published interface and check names compatible.

## Accept one finding

When a finding is intended, accept it with a reason rather than turning the rule off. It is listed apart, and comes
back when the date passes ([overrides](/docs/configuration#overrides)):

```yaml title=".github/flowpact/flowpact.config.yml"
overrides:
  - rule: FP810
    target: <the finding's symbol>
    reason: Why it is acceptable here, at least 10 characters.
    expires: YYYY-MM-DD   # optional
```

`target` is the symbol the finding is about; to list them:

```sh
flowpact lint --format json | jq -r '.findings[] | select(.code == "FP810") | .symbol'
```

## Change the severity

Change the severity (or turn the rule off) in `.github/flowpact/flowpact.config.yml`, by code or by name:

```yaml title=".github/flowpact/flowpact.config.yml"
rules:
  FP810: off
  # or: impact-under-declared: error
```

Explain it in the terminal:

```sh
flowpact explain FP810
```
