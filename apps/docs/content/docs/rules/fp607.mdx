## Why it matters

It is either dead code or called from other repositories — worth knowing before changing its interface.

## How to fix

Delete it if unused; otherwise document its external callers.

## Example

<Tabs items={["Problem", "Fixed"]}>
<Tab value="Problem">

```yaml
# .github/workflows/old-release.yml: nothing in this repository calls it
on: workflow_call
jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - run: ./release.sh
```

</Tab>
<Tab value="Fixed">

```yaml
# Deleted; or, when other repositories call it, kept with a note of who does:
# .github/workflows/release.yml, called by acme/app and acme/site
on: workflow_call
```

</Tab>
</Tabs>

## Accept one finding

When a finding is intended, accept it with a reason rather than turning the rule off. It is listed apart from the other
findings, and does not fail the build.

**On its line**, with an [ignore comment](/docs/configuration#ignore-comments) alone on the line above it (the
editor's quick fix adds it there) or at the end of the line, after any other comment such as a version
(`# v4.3.0 # flowpact: ignore[FP607] why`):

```yaml title=".github/workflows/ci.yml"
# flowpact: ignore[FP607] why it is acceptable here
<the line of the finding>
```

**In the config**, with an [override](/docs/configuration#overrides), which can expire:

```yaml title=".github/flowpact/flowpact.config.yml"
overrides:
  - rule: FP607
    target: <the finding's symbol>
    reason: Why it is acceptable here, at least 10 characters.
    expires: YYYY-MM-DD   # optional
```

`target` is the symbol the finding is about; to list them:

```sh
flowpact lint --format json | jq -r '.findings[] | select(.code == "FP607") | .symbol'
```
