## Why it matters

flowpact reads a remote action at the commit `actions.lock` pins, which is the one GitHub runs. Without the file, each action is read where its ref points now, which can be another commit with other inputs, and [`FP612`](/docs/rules/fp612) no longer compares the remote interfaces lockfile with it. GitHub still runs the pinned commits.

## How to fix

For a schema version flowpact does not read yet (it reads `v0.0.x`), upgrade flowpact. For a file that does not parse, write it again with `gh actions-lock`.

## Example

<Tab value="Problem">

# .github/workflows/actions.lock, from a gh actions-lock newer than flowpact

  '.github/workflows/ci.yml':
    - 'octo/setup@v2'
```

```

## Accept one finding

When a finding is intended, accept it with a reason rather than turning the rule off. It is listed apart from the other
findings, and comes back when the date passes ([overrides](/docs/configuration#overrides)):

```yaml title=".github/flowpact/flowpact.config.yml"
overrides:
  - rule: FP614
    target: <the finding's symbol>
    reason: Why it is acceptable here, at least 10 characters.
    expires: YYYY-MM-DD   # optional
```

`target` is the symbol the finding is about; to list them:

```sh
flowpact lint --format json | jq -r '.findings[] | select(.code == "FP614") | .symbol'
```

`*` matches within a path segment and `**` across segments, so one entry accepts every finding whose symbol matches:
`target: '**#inputs.app-id'` is that input in every workflow and action.

## Change the severity

Change the severity (or turn the rule off) in `.github/flowpact/flowpact.config.yml`, by code or by name:

```yaml title=".github/flowpact/flowpact.config.yml"
rules:
  FP614: off
  # or: actions-lock-unreadable: error
```

Explain it in the terminal:

```sh
flowpact explain FP614
```
