## Why it matters

GitHub limits how deeply reusable workflows can be nested and fails the run when the limit is exceeded. Deep chains are also where values get lost between levels.

## How to fix

Flatten the chain (call leaf workflows directly from a higher level). GitHub allows at most 10 levels; lower `limits.nestingDepth` to enforce a stricter internal limit.

## Example

<Tabs items={["Problem", "Fixed"]}>
<Tab value="Problem">

```yaml
# .github/flowpact/flowpact.config.yml
limits:
  nestingDepth: 4
# ci.yml → build.yml → package.yml → publish.yml → sign.yml: 5 workflows
```

</Tab>
<Tab value="Fixed">

```yaml
# .github/workflows/ci.yml calls the leaf workflows itself
jobs:
  build:
    uses: ./.github/workflows/build.yml
  publish:
    needs: build
    uses: ./.github/workflows/publish.yml
```

</Tab>
</Tabs>

## Accept one finding

When a finding is intended, accept it with a reason rather than turning the rule off. It is listed apart, and comes
back when the date passes ([overrides](/docs/configuration#overrides)):

```yaml title=".github/flowpact/flowpact.config.yml"
overrides:
  - rule: FP602
    target: <the finding's symbol>
    reason: Why it is acceptable here, at least 10 characters.
    expires: YYYY-MM-DD   # optional
```

`target` is the symbol the finding is about; to list them:

```sh
flowpact lint --format json | jq -r '.findings[] | select(.code == "FP602") | .symbol'
```
