flowpact ships a language server, so the analysis runs while you edit instead of only in CI. In VS Code, install
**flowpact** from the
[Visual Studio Marketplace](https://marketplace.visualstudio.com/items?itemName=flowpact.vscode-flowpact); in VSCodium,
Cursor, Windsurf and other editors built on VS Code, from
[Open VSX](https://open-vsx.org/extension/flowpact/vscode-flowpact). The extension bundles the server. Other editors
start it with [`flowpact lsp`](#other-editors). Where neither registry is reachable, install the `.vsix` from a GitHub
release: see [Install without a marketplace](#install-without-a-marketplace). You get:

- **Diagnostics as you type** — the findings of `flowpact lint` for the whole repository, closed files included,
  updated on every edit (unsaved ones too). Editing a reusable workflow updates its callers' findings at once. When
  `.github/flowpact/contracts/` exists, `flowpact check`'s contract findings (`FP801`–`FP805`) are included.
- **Hover** — how an input, secret, output, env variable or matrix key is declared, where its value comes from and
  where it flows, through every level of nesting.
- **Go to definition** across workflow calls and local actions: from `with: config:` to the callee's input, from
  `needs.build.outputs.url` to the reusable workflow's output, from `steps.x.outputs.y` to the action's output. Into
  [other repositories' workflows and actions](#remote-workflows-and-actions) too, once their sources are cached.
- **Find references** and **highlights** across files.

<Screenshot name="editor-diagnostics" format="png" alt="VS Code showing FP401 on matrix.config in tests.yml: the windows matrix entry has no config, with the call chain and flowpact's hover card" caption="A finding as you type: the windows matrix entry passes an empty config to run-suite.yml." />

The server treats every directory with a `.github` folder as a repository, so monorepos and nested repositories work
without configuration: the workspace folders are analyzed when the editor starts, and a repository nested inside one
once you open one of its files. Your [config](/docs/configuration) (severities, overrides, ignores) applies as in the
CLI.

## Install without a marketplace

Each [GitHub release](https://github.com/ciatlas/flowpact/releases) attaches the extension as
`flowpact-vscode-X.Y.Z.vsix`, the same file published to the Marketplace and Open VSX, with its signed provenance. Where
your network or policy blocks both registries:

1. **Download** the `.vsix` from the release's **Assets**, or with the GitHub CLI:

   ```sh
   gh release download vX.Y.Z --repo ciatlas/flowpact --pattern 'flowpact-vscode-*.vsix*'
   ```

2. **Verify** that the release workflow built it (optional, recommended; see [Verify a release](/docs/security#verify-a-release)).
   Online, or offline against the bundle attached next to it:

   ```sh
   gh attestation verify flowpact-vscode-X.Y.Z.vsix --repo ciatlas/flowpact
   gh attestation verify flowpact-vscode-X.Y.Z.vsix --repo ciatlas/flowpact \
     --bundle flowpact-vscode-X.Y.Z.vsix.sigstore.json
   ```

3. **Install** it. In the editor, open the Extensions view, then **⋯ → Install from VSIX…**, and pick the file. Or from
   a terminal, with the editor's command line (`code`, `cursor`, `codium`, `windsurf`):

   ```sh
   code --install-extension flowpact-vscode-X.Y.Z.vsix
   ```

The extension needs VS Code 1.101 or later (or an editor built on it). It bundles the language server, so it needs no
network access once installed. An extension installed from a `.vsix` does not update itself while the registries are
unreachable: install the next release's `.vsix` the same way, over the old one. To install it for a whole team, check
the `.vsix` into a shared location and run the same command, or use your organization's extension policy.

## Hover

Hovering an input, secret, output, env variable, matrix key, job or `uses:` value shows a short card from flowpact:

- **Header:** flowpact, the kind of symbol, and a link to this section.
- **First line:** the symbol and where it belongs, with its declaration: type, required or optional, default, values.
- **From / To:** where the value comes from (callers' values, upstream outputs, contexts such as
  `github.event.pull_request.title`) and where it goes (a callee's inputs, scripts, conditions), one hop each, with any
  further entries counted. A note in parentheses qualifies an entry as in [`flowpact trace`](/docs/cli#flowpact-trace),
  such as `(when dispatched)` for a workflow input read through `github` (`github.event.inputs.<name>`,
  `toJSON(github)`). `flowpact trace` shows the whole chain.
- On a caller's `with:` or `secrets:` key, the card shows what this call passes and where the value goes in the callee.
- On a remote `uses:` value, the card shows what the [remote interfaces lockfile](/docs/remote-interfaces) records:
  the commit, the inputs, secrets and outputs, and the secrets a reusable workflow reads without declaring them (only
  `secrets: inherit` passes those), or why the reference has no entry. On a remote call's `with:` or
  `secrets:` key it shows the input or secret as recorded there, and **Find All References** lists every call that passes
  it. A read of a remote call's or action's output says whether the reference declares it. See
  [Remote workflows and actions](#remote-workflows-and-actions).

Other extensions add their own sections below it; GitHub's GitHub Actions extension, for example, describes the
key's syntax.

## Remote workflows and actions

A `uses:` of another repository (`octo/ship/.github/workflows/deploy.yml@v1`, `octo/setup@v2`) has a file to open
once its source is in your [sources cache](/docs/remote-interfaces#sources-for-the-editor), at the commit the
[lockfile](/docs/remote-interfaces) pins: `flowpact remotes update` caches what it reads, and `flowpact remotes download`
fills the cache for a lockfile someone else wrote. Then:

- **Go to definition** on the `uses:` value opens the file (at `workflow_call:` for a reusable workflow); on a `with:`
  or `secrets:` key, the input or secret there; on `needs.<job>.outputs.<name>` or `steps.<id>.outputs.<name>`, the
  output.
- **Hover** adds the workflow's or action's `name:` and the descriptions of its inputs and secrets.

Files in the cache are another repository's at a fixed commit: VS Code opens them read-only, and the server does not
analyze them. Without the source cached, the hover links to the file on its host at that commit (github.com, or your
repository's own host for GitHub Enterprise Server) and says to run `flowpact remotes download`.

## VS Code

Install **flowpact** from the
[Visual Studio Marketplace](https://marketplace.visualstudio.com/items?itemName=flowpact.vscode-flowpact), or from
[Open VSX](https://open-vsx.org/extension/flowpact/vscode-flowpact) in VSCodium, Cursor, Windsurf and other editors
built on VS Code:

```bash
code --install-extension flowpact.vscode-flowpact
```

It bundles the language server, so nothing else needs to be installed, and works in VS Code 1.101 and later. The
server starts when the workspace has workflows or an `action.yml`, at a folder's root or nested deeper, or when you open
one; other workspaces only load the extension.

It complements GitHub's [GitHub Actions](https://marketplace.visualstudio.com/items?itemName=GitHub.vscode-github-actions)
extension, which completes and validates workflow syntax file by file: flowpact adds what crosses files (the data flow
through reusable workflows and local actions, go to definition and references across them), and by default hides the
four rules both would report (`flowpact.overlappingRules`).

### Settings

| Setting | Default | Description |
| --- | --- | --- |
| `flowpact.plugins` | `true` | Load the [plugins](/docs/custom-rules) the config lists. They run JavaScript from the repository, so they never load in an untrusted workspace (Restricted Mode), whatever this setting says. |
| `flowpact.contracts` | `auto` | Report contract drift and breaking interface changes: `auto` when `.github/flowpact/contracts/` exists, `on` or `off`. |
| `flowpact.overlappingRules` | `auto` | `FP502`–`FP505` (expression syntax, schema, YAML syntax, context availability) repeat checks the [GitHub Actions](https://marketplace.visualstudio.com/items?itemName=GitHub.vscode-github-actions) extension makes. `auto` hides them in files you open in the editor while that extension runs (it checks those files, and keeps its findings after you close them); `show` or `hide` them everywhere. |
| `flowpact.hiddenRules` | `[]` | Rule codes not to show in the editor. To turn a rule off in the CLI and CI too, set it to `off` in the config. |
| `flowpact.trace.server` | `messages` | When the output's log level is Trace: `messages` names each message between VS Code and the server, `verbose` adds its content. |

**Logs:** the **flowpact** output channel (**flowpact: Show Output**). Its log level (**Developer: Set Log Level…**) is
also the server's: set it to Debug to see every stage of the analysis, or to Trace for the protocol messages too.
VS Code's own extension host log can say `Not activating extension 'flowpact.vscode-flowpact': Timed out while
searching…` in a large workspace even though flowpact runs: it then starts after VS Code's startup instead. The output
channel and the language status item show its real state.

**Commands:** **flowpact: Restart Language Server** — also needed after you edit a plugin, since a loaded plugin stays
loaded — and **flowpact: Show Output**.

### Workspace trust

In an untrusted workspace (Restricted Mode), everything works except plugins, which run code from the repository.
Trusting the workspace loads them without a restart; the language status item next to the file type says when they
are off. Plugins load only for repositories inside the workspace folders: not for a file opened from elsewhere, nor
for a repository above the folder you opened.

### Limitations

- A repository needs a `.github` folder to be analyzed in the editor; one with only an `action.yml` gets no
  diagnostics there yet (`flowpact lint` checks it).
- `env` set on a step or in a composite action, `steps.<id>.outcome` / `conclusion` and step ids are not navigable
  yet.
- Contract files (`.github/flowpact/contracts/`) show their findings but have no hover or go to definition.
- There are no quick fixes, rename or completion yet.

## Other editors

`flowpact lsp` starts the same server over stdin/stdout, for any editor with an LSP client. It needs flowpact
[installed](/docs/getting-started). Settings are read from the client's `initializationOptions`, and from
`workspace/didChangeConfiguration` under `flowpact`:

| Setting | Default | Description |
| --- | --- | --- |
| `plugins` | `false` | Load the plugins the config lists. Enable this only for repositories you trust. |
| `contracts` | `auto` | `auto`, `on` or `off`, as above. |
| `hiddenRules` | `[]` | Rule codes not to show. |
| `logLevel` | `info` | `silent`, `error`, `warn`, `info`, `debug` or `trace`, sent to the editor's log. |

### Neovim

With Neovim 0.11 or later:

```lua
vim.lsp.config('flowpact', {
  cmd = { 'flowpact', 'lsp' },
  filetypes = { 'yaml' },
  root_markers = { '.github' },
})
vim.lsp.enable('flowpact')
```

To use the plugins the config lists, add `init_options = { plugins = true }`.
