| [`flowpact remotes update`](#flowpact-remotes-update) | Fetch the interfaces of the remote workflows and actions this repository (or the given workflows and actions) uses into the [remote interfaces lockfile](/docs/remote-interfaces). |
| [`flowpact remotes download`](#flowpact-remotes-download) | Download the sources of the commits the lockfile pins into the [sources cache](/docs/remote-interfaces#sources-for-the-editor), for the editor. |
| [`flowpact remotes clean`](#flowpact-remotes-clean) | Empty the sources cache, or keep the most recently used commits of each repository. |
| [`flowpact graph`](#flowpact-graph) | Show the call graph of workflows and actions. |
| [`flowpact trace`](#flowpact-trace) | Follow a value down to where it is used, or up to where it comes from. |
| [`flowpact explain`](#flowpact-explain) | Print the docs for a rule. |
| [`flowpact rules`](#flowpact-rules) | List the rules and their effective severities. |
| [`flowpact lsp`](#flowpact-lsp) | Start the language server for editors. |

Every command but `lsp` is also a function of the [API](/docs/api), for programs that run flowpact themselves.

Options go after the command (`flowpact lint --no-plugins`); an option before it is a usage error. The value of an
option is only ever that option's value, whatever it looks like: `--title "$PR_TITLE"` with a title of `--help` or
`--plugin=x` is just a title.

The analysis commands (`lint`, `check`, `impact`, `generate`, `trace`) start by printing the tool version and the
version of every schema they read or write (to stderr, so JSON on stdout stays clean):

```text
 flowpact  v0.21.0  config schema v1 · contract schema v1 · report schema v1 · node v24.4.0
root . · config .github/flowpact/flowpact.config.yml
```

`flowpact --version` prints the same line.

## `flowpact lint`

Analyzes all workflows and local actions and reports findings.

```sh
flowpact lint [paths…] [options]
```

<Screenshot name="lint-deep-nesting" alt="flowpact lint output for a four-level chain of reusable workflows" caption="Nested reusable workflows: a missing required input two levels down, an undeclared output, a needs edge that is missing." />

| Option | Description |
| --- | --- |
| `[paths…]` | Files or directories to report on. Everything is still analyzed. With `--impact`, impact mode grades only the published workflows and actions within them (see [`flowpact impact`](#flowpact-impact)). |
| `--root <dir>` | Repository root (default: current directory). |
| `--config <file>` | Config file (default: `.github/flowpact/flowpact.config.yml`). |
| `--base-config <file>` | Defaults under the repository's config, such as an organization's, relative to the working directory. See [Base config](/docs/configuration#base-config). |
| `--no-plugins` | Do not load the [plugins](/docs/custom-rules) the config lists; they run code from the repository. |
| `--plugin <file>` | Also load this plugin, relative to the working directory; repeatable, and not affected by `--no-plugins`. See [organization rules](/docs/integrating#organization-rules). |
| `--format pretty\|json\|markdown\|sarif\|github` | Output on stdout (default `pretty`). See [output formats](#output-formats). |
| `-o, --output <file>` | Also write the report to a file, replacing it; format by extension: `.sarif` / `.sarif.json` → SARIF, `.json` → JSON, `.md` → Markdown, anything else → plain text. Name the format for other names, as in `-o markdown:"$GITHUB_STEP_SUMMARY"`. Repeat it to write several reports from one run. |
| `--fail-on error\|warning\|never` | Exit `1` when findings at this level exist (default `error`). |
| `--only <codes>` | Comma-separated codes or names to run, e.g. `FP401,unused-input`. |
| `--hide-info` | Pretty terminal output only: do not list info findings (they are still counted). JSON, Markdown and SARIF always include them. |
| `--include-graph` | Add the data-flow graph to JSON output and the call graph (Mermaid) to Markdown output. |
| `--dump-graph <file>` | Write the data-flow graph as JSON (debugging). |
| `--no-schema` | Skip validation against GitHub's workflow schema. |
| `--fetch-remotes` | Fetch the interfaces of the remote workflows and actions the [remote interfaces lockfile](/docs/remote-interfaces) lacks, for this run only (nothing is written), with `GH_TOKEN`, `GITHUB_TOKEN` or the GitHub CLI's token. A reference that cannot be fetched is a warning. |
| `--impact` | Also check the release impact of the changes against the declared impact, with `--base <ref>`, `--expect none\|patch\|minor\|major`, `--title <text>` and `--labels <a,b>`. See [`flowpact impact`](#flowpact-impact). |
| `-d, --debug` | Debug logging (see below). |
| `-v` / `-vv` | Verbose / trace logging. |
| `-q, --quiet` | No banner or logs, only the report and errors. |
| `--no-color` | Disable colors (also `NO_COLOR=1`). |
| `--ascii` | ASCII-only symbols for limited terminals. |

### Output formats

| Format | Use it for |
| --- | --- |
| `pretty` | The terminal: code frames, call chains, matrix combinations and a summary card. |
| `json` | Tooling. Follows [`/schemas/report/v1.json`](/schemas/report/v1.json) (below). |
| `markdown` | Job summaries and pull request comments: counts, findings grouped by severity with docs links, and contract changes in `flowpact check`. Inside GitHub Actions, locations link to the file at the commit being checked. |
| `sarif` | [SARIF 2.1.0](https://docs.oasis-open.org/sarif/sarif/v2.1.0/sarif-v2.1.0.html) for GitHub code scanning and other SARIF viewers. Findings accepted by overrides are left out (code scanning ignores SARIF suppressions); the JSON report lists them under `suppressed`. |
| `github` | GitHub Actions: one [workflow command](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands) per finding, which GitHub shows as an error, warning or notice annotation on the file and line, in the run and the pull request — the same annotations as the [action](/docs/action#annotations). Stdout only. |

Inside GitHub Actions, when `--root` is a subdirectory of the repository, the paths in `github` annotations, SARIF and
the Markdown links are made relative to the repository (`GITHUB_WORKSPACE`), where GitHub resolves them.

```sh
flowpact lint -o flowpact-report.json           # JSON file + pretty output in the terminal
flowpact lint -o flowpact.sarif                 # SARIF file for code scanning
flowpact lint -o flowpact-report.md             # Markdown file, e.g. for $GITHUB_STEP_SUMMARY
flowpact lint -o flowpact-report.txt            # plain-text copy of the pretty report
flowpact lint --format json > report.json  # JSON only

# In GitHub Actions: annotations, the job summary and SARIF, from one run
flowpact lint --format github -o markdown:"$GITHUB_STEP_SUMMARY" -o flowpact.sarif
```

### JSON report

The JSON report follows [`/schemas/report/v1.json`](/schemas/report/v1.json):

```json
{
  "$schema": "https://ciatlas.github.io/flowpact/schemas/report/v1.json",
  "meta": { "tool": "flowpact", "version": "0.21.0", "schemas": { "config": 1, "contract": 1, "report": 1 }, "node": "v24.4.0", "platform": "linux-x64", "root": "/home/runner/work/app/app", "durationMs": 31 },
  "summary": { "errors": 1, "warnings": 0, "infos": 0, "suppressed": 0, "byCode": { "FP401": 1 } },
  "findings": [
    {
      "code": "FP401",
      "name": "empty-binding-for-matrix-combo",
      "severity": "error",
      "message": "Input \"config\" for .github/workflows/run-suite.yml is empty in 1 of 3 matrix combinations — matrix.config is not defined there",
      "loc": { "file": ".github/workflows/tests.yml", "line": 23, "column": 19, "endLine": 23, "endColumn": 32 },
      "related": [{ "loc": { "file": ".github/workflows/tests.yml", "line": 18, "column": 13 }, "message": "this include entry has no `config`" }],
      "combos": ["{ name: windows }"],
      "symbol": ".github/workflows/run-suite.yml#inputs.config",
      "why": "…", "fix": "…",
      "docsUrl": "https://ciatlas.github.io/flowpact/docs/rules/fp401",
      "fingerprint": "3f2a9c0d81b7e645"
    }
  ],
  "suppressed": [],
  "rules": [{ "code": "FP101", "name": "missing-required-input", "severity": "error" }, "…"]
}
```

- `symbol` identifies what the finding is about; use it as the `target` of an
  [override](/docs/configuration#overrides).
- `suppressed` lists findings accepted by overrides, each with an `override` object (`index`, `reason`, `expires`,
  `owner`); they are not part of the counts.
- In `flowpact check`, `contracts` holds the contract comparison: `drift`, the number of `breaking` changes, `counts` per
  status and one entry per contract file with its status and semantic changes.
- `fingerprint` is stable across unrelated edits (line shifts, changed counts), so it can be used to track findings
  over time.
- `rules` lists every rule with its code, name and effective severity (`off` included).
- With `--impact` (or `flowpact impact`), `impact` holds the verdict: the `baseline`, the `required` and `declared`
  impact, `ok`, and every graded change. With paths, `impact.scope` lists the `paths` and the published `units`
  within them, the only ones graded; `impact.ignored` lists the published units `ignore` left out. See
  [Impact mode](/docs/impact-mode).

## `flowpact check`

Everything `flowpact lint` does, plus a comparison with the [contracts](/docs/contracts) committed in
`.github/flowpact/`.

```sh
flowpact check [paths…] [options] [--patch <file>]
```

It takes the same options as `flowpact lint`. Contract findings — missing (`FP801`), outdated (`FP802`), breaking
(`FP803`), orphaned (`FP804`) and invalid (`FP805`) contracts — are errors by default, so the command exits `1`
until the contracts are regenerated.

With `paths`, the comparison covers the contracts of those workflows and actions, and the contracts that list them as
a consumer: a caller that stops passing an input or reading an output changes its callee's contract, so that drift
is reported too. The orphaned contract of a workflow or action that no longer exists is covered when its path lies
within the paths, such as `actions/` for a removed `actions/old` (with `--impact`, the removed path itself counts).

| Option | Description |
| --- | --- |
| `--patch <file>` | When contracts drifted, also write a `git apply`-able patch with the regenerated contracts. |

## `flowpact generate`

Writes the contract for every workflow and local action, and deletes contracts whose workflow or action no longer
exists.

```sh
flowpact generate [paths…] [--dry-run] [--patch <file>] [--out <dir>]
```

| Option | Description |
| --- | --- |
| `[paths…]` | Workflow or action files or directories: write only their contracts and the contracts that list them as a consumer, and delete the orphaned contracts of removed units within them (what `flowpact check` with the same paths compares). Other contracts are left alone. |
| `--dry-run` | Print the table of changes and a colored unified diff; write nothing. |
| `--patch <file>` | Write the changes as a `git apply`-able patch instead of applying them. |
| `--out <dir>` | Write all contracts (changed or not) under `<dir>`, keeping their relative paths, instead of the repository. Nothing is deleted. |

It also accepts `--root`, `--config`, `--base-config` and the logging and color options. The table lists every contract file as new,
changed, removed or unchanged, with the semantic changes underneath; breaking changes are marked. Running it twice
in a row changes nothing.

<Screenshot name="generate-dry-run" alt="flowpact generate --dry-run listing new contract files and a unified diff of their contents" />

## `flowpact remotes`

The [remote interfaces](/docs/remote-interfaces) of the workflows and actions this repository calls from other
repositories: `update` writes the lockfile, `download` fills the sources cache from it for the editor, and `clean`
empties that cache.

### `flowpact remotes update`

Fetches the interface of every remote reusable workflow and action the repository uses, and writes
`.github/flowpact/remotes.lock.yaml` (see [Remote interfaces](/docs/remote-interfaces)).

```sh
flowpact remotes update [paths…] [--cache-dir <dir> | --no-cache] [--dry-run] [--fail-on <verdict>] [--format json]
```

| Option | Description |
| --- | --- |
| `[paths…]` | Workflow or action files or directories: fetch only the remote references they use, and those of the local workflows and actions they call. Other entries of the lockfile are kept as they are; an entry nothing in the repository uses any more is still dropped. |
| `--github-com` | On GitHub Enterprise Server or GHE.com: also look on github.com for the references the enterprise server lacks, as GitHub Connect does, with `GITHUB_COM_TOKEN` or none (never the enterprise token). See [GitHub Enterprise Server](/docs/remote-interfaces#github-enterprise-server-and-ghecom). |
| `--cache-dir <dir>` | flowpact's cache directory: keep the files read in its `remotes` directory (relative to where you run flowpact). Also in CI, where nothing is kept by default. |
| `--no-cache` | Keep none of the files read; write only the lockfile. Not with `--cache-dir`. |
| `--dry-run` | Fetch and say what would change; write nothing, not even to the cache. |
| `--fail-on <verdict>` | Also exit `1` when a changed entry breaks a call of the repository (`breaks`), or breaks one or leaves part of one unchecked (`unchecked`). Default: `never`. See [When a version changes](/docs/remote-interfaces#when-a-version-changes). |
| `--format <format>` | `pretty` (the default) or `json`: the result as [`remotesUpdate()`](/docs/api#remotesupdate-remotesdownload-and-remotesclean) returns it. `remotes download` and `remotes clean` take it too. |

It also accepts `--root`, `--config` and the logging and color options. Each reference is resolved to a commit
through the GitHub API, and its workflow file or `action.yml` is read at that commit. Entries of references nothing uses
any more are dropped. A reference that does not exist, or that the token cannot read, is listed as `unread` and, without
a previous entry, recorded under the lockfile's `unreadable:`, so [`FP612`](/docs/rules/fp612) counts it as accounted
for. Any other failure (the network, a timeout, an error from the API, a file over 1 MB) is listed as `failed`, keeps
the reference's previous entry, and makes the command exit `1`.

A reference GitHub's [`actions.lock`](/docs/remote-interfaces#githubs-actionslock) pins is read at the commit it pins,
not at the one its tag points to now; the output says how many were (`.github/workflows/actions.lock: 2 references read
at the commits it pins`), or why that file is not used.

Each entry that changed (its reference moved to another commit, or its interface changed) is graded against every call
of the reference in the repository, also with paths: under the reference, the output lists the interface changes and
each call the change breaks or leaves partly unchecked, with why (see
[When a version changes](/docs/remote-interfaces#when-a-version-changes)).

The token is `GH_TOKEN`, else `GITHUB_TOKEN`, else the GitHub CLI's (`gh auth token`); the output names the source it
used (`token: GH_TOKEN`), never the token, which is sent only to the GitHub API (`GITHUB_API_URL` on GitHub Enterprise
Server). Public repositories can be read without one, at GitHub's 60 requests an hour for anonymous reads; private and
internal ones need read access to their contents (fine-grained: **Contents: read** on them; classic: `repo`). In a
terminal it shows a count as it fetches; `-v` or `-d` logs each reference instead. Each failure says why and what to do:
see [Remote interfaces](/docs/remote-interfaces#when-a-reference-is-not-fetched).

The files it reads go to the [sources cache](/docs/remote-interfaces#sources-for-the-editor), for the editor; the
output names it (`sources: ~/.cache/flowpact/remotes (2 new)`). Files it cannot keep there are counted on that line,
with the first reason (`-d` logs each one), and do not fail the command. With `--dry-run`, nothing is kept. In CI
(`CI` set, or Azure Pipelines' `TF_BUILD`, or Jenkins' `JENKINS_URL`), nothing is kept unless `--cache-dir` or
`FLOWPACT_CACHE_DIR` says where: nobody opens the files there, and the line says so.

### `flowpact remotes download`

Downloads the workflow files and `action.yml`s of the remote references the repository uses into the
[sources cache](/docs/remote-interfaces#sources-for-the-editor), at the commits the lockfile pins, so the editor can
open them. It resolves no tag and does not change the lockfile.

```sh
flowpact remotes download [paths…] [--cache-dir <dir>] [--github-com]
```

| Option | Description |
| --- | --- |
| `[paths…]` | Workflow or action files or directories: download only the sources of the remote references they use, and those of the local workflows and actions they call. |
| `--cache-dir <dir>` | flowpact's cache directory: download into its `remotes` directory (relative to where you run flowpact). |
| `--github-com` | Download the sources of entries read on github.com (`host: github.com`), with `GITHUB_COM_TOKEN` or none; without it they are skipped. See [GitHub Enterprise Server](/docs/remote-interfaces#github-enterprise-server-and-ghecom). |

It needs the lockfile (without one, or with one it cannot use, it exits `2`), and the same token and `GITHUB_API_URL`
as `flowpact remotes update`. Unlike `remotes update`, it uses the cache in CI too: downloading is all it does.
A source the cache has is not downloaded again. A reference the lockfile has no entry for is listed as `unlocked`
(`flowpact remotes update` adds it), one it records as not readable as `skipped`. A source that cannot be downloaded or
kept is listed as `failed`, and makes the command exit `1`.

Both commands then keep the 3 most recently used commits of each repository they used, and never one they used; the
output counts the older commits removed. See [`flowpact remotes clean`](#flowpact-remotes-clean) to clean more.

### `flowpact remotes clean`

Removes the commits kept in the [sources cache](/docs/remote-interfaces#sources-for-the-editor).

```sh
flowpact remotes clean [--keep <n>] [--cache-dir <dir>]
```

| Option | Description |
| --- | --- |
| `--keep <n>` | Keep the `n` most recently used commits of each repository (used by `remotes update` or `remotes download`); without it, nothing is kept. |
| `--cache-dir <dir>` | flowpact's cache directory, as for `remotes update`. |

It removes only the `<owner>/<repo>/<sha>` directories flowpact keeps there, then the directories they leave empty;
anything else in the directory stays. A commit it cannot remove is named in the output and makes it exit `1`.

## `flowpact graph`

Shows which workflows call which reusable workflows and local actions.

```sh
flowpact graph [paths…] [--format tree|mermaid|dot|json]
```

With paths (workflow or action files, or directories), the graph starts from those workflows and actions and shows
only what they call and use, all the way down; every format draws the same part, and the JSON lists them as `roots`.
The tree starts at them even when one is in a cycle. Without paths, it shows the whole repository.

| Format | Output |
| --- | --- |
| `tree` (default) | A tree per top-level workflow in the terminal. |
| `mermaid` | A Mermaid `flowchart`, rendered by GitHub in Markdown files, issues and pull requests. |
| `dot` | Graphviz DOT, e.g. `flowpact graph --format dot \| dot -Tsvg > graph.svg`. |
| `json` | Nodes and edges for tooling. |

Edges are labelled with the calling job (`jobs.build`, or the step for local actions), `×N` when the call fans out over
N matrix combinations, and `(inherit)` for `secrets: inherit`. Reusable workflows in other repositories appear as
**remote** nodes, local targets that do not exist as **missing** nodes, and job-level calls to files outside
`.github/workflows` ([`FP606`](/docs/rules/fp606)) as **invalid location** nodes.

## `flowpact trace`

Shows where a value flows to, or with `--up` where it comes from.

```sh
flowpact trace <symbol> [--up] [--depth n] [--format pretty|json]
```

Each symbol is expanded once per trace; where the same value is reached again through another path (for example
shared callees), the tree says `↑ shown above` instead of repeating it. `--format json` always prints
`{ "query", "direction", "traces": [...] }`, however many symbols matched; for a workflow or action without inputs,
secrets or outputs, `traces` is empty and `"unit"` names it.

Symbols can be written in several ways:

| Query | Matches |
| --- | --- |
| `.github/workflows/ci.yml#inputs.env` | exactly that symbol |
| `ci.yml#inputs.env` | by file name |
| `ci.yml:env` | inputs, secrets or outputs named `env` |
| `ci.yml` | the whole interface of the workflow (every input, secret and output) |

<Screenshot name="trace-down" alt="flowpact trace following an input through four levels of reusable workflows" caption="Downstream: an input passed through three levels and finally used as the deployment environment." />

<Screenshot name="trace-up" alt="flowpact trace --up showing the matrix values feeding an input, with one combination missing" caption="Upstream: the input is fed by matrix.config, which one combination does not define." />

Under each branch, `via` shows how the value gets there: the expression it passes through, `workflow output` or
`action output`, or `secrets: inherit`. A note in parentheses qualifies it where that matters: `(jobs.deploy)` names the
job whose `secrets: inherit` passes a secret on, `(exposed to the caller)` marks an output of a reusable workflow or
action that becomes the output of the job or step that uses it, and `(the default of inputs.<name>)` and `(when dispatched)` are
described below.

Upstream, each `◀` branch is a value the symbol is computed from, traced further up in turn. Where the trace ends, the
tree says what it ends at:

| Leaf | The value comes from |
| --- | --- |
| `literal` | a plain value: what a caller or a step passes, an env variable's or output's own value, or the input's `default:` when a caller or step omits the input |
| `omitted` | nothing: a caller or step does not pass the input (the `default:` GitHub then uses, if any, is listed too) |
| `value`, `missing`, `dynamic` | a matrix key: its value in each combination, a combination that does not define it, or a matrix computed at runtime |
| `context` | a context flowpact does not follow: `github.event.pull_request.title`, `runner.os`, `needs.<job>.result`, `steps.<id>.outcome`, or an `env` variable set at runtime (`$GITHUB_ENV`). A value read from the step's own `env:` is followed to what that entry reads. |
| `invalid` | an expression that does not parse ([`FP502`](/docs/rules/fp502) reports it), or, in an input's `default:`, a context or function GitHub does not allow there |
| `expression` | an expression that reads no context, such as `format('v{0}', 1)` |

When a caller or step omits an input, its `default:` is the value there, so the trace also ends at the default (its
leaves come after the callers' leaves; the symbols it reads are `◀` branches, which come first): a `literal` for a
plain default, or what an expression default reads, at
`<action> › inputs.<name>.default` (`<workflow> › on.workflow_call.inputs.<name>.default` in a reusable workflow).
GitHub evaluates a default with a few contexts only:

- a reusable workflow's input: `github`, `inputs` and `vars`. The default applies when the workflow is called, so the
  `workflow_call` inputs and the variables it names (`inputs.<name>`, `vars.<NAME>`) are followed as `◀` branches,
  noted `(the default of inputs.<name>)`; a whole `inputs` (`toJSON(inputs)`) is a branch for each `workflow_call`
  input. An input declared only under `workflow_dispatch` (or nowhere) is empty there, a whole `vars` (`vars.*`) names
  no single variable, and `github` is the caller's, so `github.event.inputs.<name>` is not the workflow's own input:
  each is a `context` leaf;
- an action's input: the calling job's `github`, `strategy`, `matrix`, `job` and `runner`, each a `context` leaf. It
  may also call `hashFiles()`, which reads no context: `${{ hashFiles('**/package-lock.json') }}` alone ends at an
  `expression` leaf.

Any other context in a default (`env`, `secrets`, `steps`, `needs`, or an action's `inputs` and `vars`) is an `invalid`
leaf, as is a status function such as `success()`, or `hashFiles()` in a reusable workflow's default. A default that no
caller falls back to is not shown, nor is the default of a required reusable-workflow input: GitHub fails the run when
a caller omits it ([`FP101`](/docs/rules/fp101)).

Here a local action's `token` defaults to `github.token`, and neither step that uses the action passes it:

```text
$ flowpact trace setup:token --up
.github/actions/setup#inputs.token  .github/actions/setup/action.yml:4:3 (input)
├── omitted in .github/workflows/ci.yml › jobs.build › steps[1]  .github/workflows/ci.yml:8:15
│   (not passed)
├── omitted in .github/workflows/ci.yml › jobs.test › steps[1]  .github/workflows/ci.yml:13:15
│   (not passed)
└── context in .github/actions/setup › inputs.token.default  .github/actions/setup/action.yml:4:65
    github.token
```

A `context` leaf shows where outside data enters. Here a reusable workflow's input carries a pull request's title, text
its author controls, while another caller passes its own input and the branch or tag it runs on:

```text
$ flowpact trace notify.yml:message --up
.github/workflows/notify.yml#inputs.message:4:7 (input)
├── ◀ .github/workflows/release.yml#inputs.version:4:7 (input)
│   via Released ${{ inputs.version }} from ${{ github.ref_name }}  @ .github/workflows/release.yml:9:29
├── context in .github/workflows/pr.yml › jobs.notify  .github/workflows/pr.yml:6:20
│   github.event.pull_request.title
└── context in .github/workflows/release.yml › jobs.notify  .github/workflows/release.yml:9:56
    github.ref_name
```

flowpact does not judge whether such a value is safe where it is used. [zizmor](https://github.com/zizmorcore/zizmor)
reports expressions expanded into scripts (template injection); pass them through `env:` instead.

A workflow that can be both called and dispatched holds an input in `github.event.inputs.<name>` only when it is
dispatched. When it is called, GitHub gives it the caller's `github` context, so `github.event.inputs` is the caller's
event, never what the caller passes in `with:`. Upstream, such a read shows the input as a branch noted
`(when dispatched)`, with nothing traced under it, next to a `context` leaf for the called case; downstream, an input
reached through a caller's `with:` does not go on through its `github.event.inputs` reads. The same holds for a whole or
computed `github` (`toJSON(github)`, `github.event[x]`), which reads every dispatch input, and for the step's own `env:`
values that read `github`. Read it as `inputs.<name>`, which holds the value in both cases. Here `release.yml` calls
`deploy.yml` with `environment: production`, a value that never reaches the action:

```text
$ flowpact trace ship:environment --up
.github/actions/ship#inputs.environment  .github/actions/ship/action.yml:4:3 (input)
├── ◀ .github/workflows/deploy.yml#inputs.environment:4:7 (input)
│   via ${{ github.event.inputs.environment }} (when dispatched)  @ .github/workflows/deploy.yml:16:28
└── context in .github/workflows/deploy.yml › jobs.deploy › steps[1]  .github/workflows/deploy.yml:16:28
    github.event.inputs.environment
```

A whole object or a computed key reads every member: `toJSON(inputs)`, `inputs[inputs.which]`, `toJSON(matrix)`,
`secrets[inputs.name]` and `toJSON(env)` are a `◀` branch for each input, matrix key, secret or env variable the files
declare, and downstream a use of each. A whole `secrets` is also a `◀` branch for each secret the workflow reads by name
or is passed by name, and for `GITHUB_TOKEN`, which every workflow has. A workflow that callers hand every secret to
through `secrets: inherit` gets every secret they have, so there a whole `secrets` is also a `◀` branch for each secret
those callers declare, read by name or are passed by name, and downstream a caller's secret goes through
`secrets: inherit` into it, as into a workflow that may read every secret: one with an expression that does not parse,
or that hands every secret on to a remote workflow. Secret names ignore case, so `secrets: inherit` follows a secret to
the other workflow's own spelling of it: the one it declares, else each spelling it reads or a caller passes it by. It
never hands on `GITHUB_TOKEN`, which GitHub gives every workflow itself. Where the object can hold members the files do
not declare, it also stays a `context` leaf: `env` (written at runtime), `secrets` (secrets no file names, and through
`secrets: inherit` the callers'), an action's `inputs` (the runner passes every `with:` key) and a matrix computed at
runtime, in whole or in its `include`. Variables are set in the repository's settings, so a whole `vars` is only a
`context` leaf. Here a reusable workflow passes all its inputs to an action, and the caller omits `profile`:

```text
$ flowpact trace report:settings --up
.github/actions/report#inputs.settings  .github/actions/report/action.yml:4:3 (input)
├── ◀ .github/workflows/build.yml#inputs.target:4:7 (input)
│   via ${{ toJSON(inputs) }}  @ .github/workflows/build.yml:14:32
│   └── literal in .github/workflows/ci.yml › jobs.build  .github/workflows/ci.yml:7:15
│       "linux"
└── ◀ .github/workflows/build.yml#inputs.profile:5:7 (input)
    via ${{ toJSON(inputs) }}  @ .github/workflows/build.yml:14:32
    ├── omitted in .github/workflows/ci.yml › jobs.build  .github/workflows/ci.yml:5:11
    │   (not passed)
    └── literal in .github/workflows/build.yml › on.workflow_call.inputs.profile.default  .github/workflows/build.yml:5:41
        "release"
```

## `flowpact impact`

For publishers of reusable workflows and actions: checks that the release impact a pull request declares covers the
changes to published units since its base. See [Impact mode](/docs/impact-mode).

```sh
flowpact impact [paths…] --base origin/main --title "fix: tidy the test job"
```

It runs only the impact rules (`FP810`–`FP814`), so its exit code reflects only the verdict. `flowpact lint --impact`
and `flowpact check --impact` add the verdict to everything else they report. Options: `--base`, `--expect`,
`--title`, `--labels` and the output options of `lint`.

With paths (workflow or action files, or directories), impact mode grades only the published workflows and actions
within them, and the verdict is about those alone: the paths narrow the gate, so a change to a published unit
outside them is not checked. A path the pull request removed counts when the baseline has a workflow or action there,
whether it is given relative to `--root` or to the working directory.
The same holds for `lint --impact` and `check --impact` with paths. See [Impact mode](/docs/impact-mode#only-some-units).

## `flowpact lsp`

Starts the language server, which speaks the Language Server Protocol over stdin/stdout (`--node-ipc` and
`--socket <port>` are also accepted). Editors start it themselves; you do not run it by hand. It serves diagnostics as
you type, hover traces, go to definition across workflow calls, and references. See [Editors](/docs/editors) for its
settings and how to set it up in Neovim and other editors; the VS Code extension bundles it.

## Debug mode and logging

flowpact logs every stage of the analysis: config resolution, file discovery, parsing per file, graph construction,
matrix expansion per job (combinations, keys, exactness), each rule with its finding count and timing, and the
final summary.

| Enable with | Level |
| --- | --- |
| `--debug`, `-d`, `-v`, `FLOWPACT_DEBUG=1` | debug |
| `-vv`, `FLOWPACT_DEBUG=trace` | trace (adds per-file timings and skipped rules) |
| `RUNNER_DEBUG=1`, `ACTIONS_STEP_DEBUG=true` | debug — set automatically when you re-run a GitHub job with debug logging |

Logs go to stderr, so `--format json` output stays parseable.

## Exit codes

| Code | Meaning |
| --- | --- |
| `0` | No findings at or above `--fail-on` (default: `error`). |
| `1` | Findings at or above `--fail-on` — including contract findings in `flowpact check`. |
| `2` | Usage or configuration error (unknown rule, invalid config, plugin that fails to load, nothing to analyze). |
| `3` | Internal error — please [report it](https://github.com/ciatlas/flowpact/issues) with `--debug` output. |

`flowpact graph`, `flowpact trace`, `flowpact explain` and `flowpact rules` exit `0` on success. `flowpact generate`
exits `0` too, or `1` when a file with YAML syntax errors could not be regenerated (its committed contract is kept).

## Environment variables

| Variable | Effect |
| --- | --- |
| `NO_COLOR` / `FORCE_COLOR` | Disable / force colors. |
| `FLOWPACT_DEBUG` | `1` for debug logs, `trace` for trace logs. |
| `FLOWPACT_NO_HYPERLINKS` | Disable clickable docs links (OSC 8). |
| `GITHUB_REPOSITORY` | `owner/repo`, used to resolve same-repository `uses:` references (also read from `.git/config` or the `repository` config key). |
| `GH_TOKEN` / `GITHUB_TOKEN` | The token `flowpact remotes update`, `remotes download` and `--fetch-remotes` read remote repositories with (else `gh auth token`). |
| `GITHUB_API_URL` | The GitHub API `flowpact remotes update`, `remotes download` and `--fetch-remotes` use (`https://<host>/api/v3` on GitHub Enterprise Server); `https://api.github.com` by default. |
| `GITHUB_COM_TOKEN` | With `--github-com`, the token for github.com; without it, github.com is read without one. |
| `FLOWPACT_CACHE_DIR` | An absolute path: keep the [sources cache](/docs/remote-interfaces#sources-for-the-editor) in its `remotes` directory instead of the platform's per-user cache, also in CI. `--cache-dir` takes precedence. |
| `CI` / `TF_BUILD` / `JENKINS_URL` | Set by CI services: `flowpact remotes update` keeps no sources unless `--cache-dir` or `FLOWPACT_CACHE_DIR` says where. |
| `COLUMNS` | Output width when not attached to a terminal. |
